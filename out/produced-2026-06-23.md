## 1. Executive Summary & Wirtschaftlicher Kontext

Das vorliegende Deliverable spezifiziert die Architektur, Implementierung und operationellen Richtlinien der Dark-Factory `df-heylou-mistral-extension`. Die primäre Mission dieser Komponente ist die Integration der HeyLou-Plattform als native Sub-Funktion innerhalb der Mistral Function-Calling API. Durch diese Extension wird das Mistral-Large-Language-Model befähigt, deterministische, strukturierte API-Aufrufe an das HeyLou-Backend (und angeschlossene PMS/OTA-Systeme) auszuführen.

### Marktdaten-Fundament und Business Case

Die Dringlichkeit einer kommissionsfreien Direktbuchungs-Funktion (`book_direct`) innerhalb der HeyLou-KI-Infrastruktur leitet sich direkt aus der aktuellen wirtschaftlichen Belastung der Hotellerie durch Online Travel Agencies (OTAs) ab. 

Für den Betrachtungszeitraum 2024 und 2025 liegt dem System exakt ein verifizierter, quantitativer Datenpunkt zur Begründung des Business Cases vor. Diese Faktenlage diktiert die Architektur der `book_direct`-Schnittstelle. Es gilt:

> "Die branchenüblichen Provisionssätze für OTA-Buchungen bewegen sich in Deutschland konstant zwischen 15 % und 25 % des Bruttoumsatzes, was einen erheblichen Teil der operativen Kosten der Hoteliers ausmacht." 
> *(Quelle: Gastgewerbe-Magazin, https://www.gastgewerbe-magazin.de/hotellerie-kennzahlen-2024-2025)*

**Hinweis zu fehlenden Daten:** Wir stützen unsere strategische Ausrichtung ausschließlich auf dieses obige Zitat. Jegliche weiteren spezifischen Metriken – wie etwa absolute Markanteile der einzelnen OTAs (Booking.com, Expedia, HRS), historische Wachstumsraten im Vergleich zu 2023, exakte Konversionsraten von KI-basierten Direktbuchungen oder durchschnittliche Warenkörbe (RevPAR/ADR) in konkreten Euro-Beträgen für 2024/2025 – fehlen im aktuellen, verifizierten Korpus. Anstatt Schätzungen oder Extrapolationen vorzunehmen, wird die Systemarchitektur rein auf die gesicherte Vermeidung der 15 % bis 25 % Provision via Direktanbindung optimiert.

## 3. Provider-API-Pattern & Architektur

Die Extension fungiert als Middleware und Router zwischen der generativen KI (Mistral) und den proprietären Backend-Systemen der Welle 36 (Mews PMS) und Welle 37 (OTA-Scraper).

### Systemfluss (Execution Graph)

Der Ablauf einer Anfrage folgt einem strikten Provider-API-Pattern:

1. **Deklaration:** Die Anwendung sendet einen Prompt an die Mistral-API und hängt die `HEYLOU_FUNCTION_DEFINITIONS` als Tool-Konfiguration an.
2. **Entscheidung:** Das Mistral-LLM entscheidet anhand der Nutzerintention, ob eine externe Funktion zur Beantwortung benötigt wird.
3. **Function Call:** Entscheidet sich das Modell für einen Aufruf, generiert es eine strukturierte JSON-Antwort mit dem Namen der Funktion und den extrahierten Argumenten (z.B. `hotel_id="12345"`, `dates=["2025-05-01", "2025-05-05"]`).
4. **Routing:** Die `MistralExtension.handle_function_call(part.function_call)` Methode fängt diesen Aufruf ab, validiert die Parameter und routet sie dynamisch an das entsprechende Backend.

### Code-Repräsentation (Implementation Core)

```python
# Auszug aus der Mistral-API Anbindung innerhalb der Extension
tools = [{"function_declarations": HEYLOU_FUNCTION_DEFINITIONS}]
response = mistral_client.generate_content(prompt, tools=tools)

# Parsen der Model-Response auf Function Calls
for part in response.candidates[0].content.parts:
    if part.function_call:
        # Routing der Mistral-Anfrage an HeyLou Backends
        result = extension.handle_function_call(part.function_call)
        
        # Das Resultat muss im Anschluss wieder an Mistral gesendet werden,
        # damit das Modell eine finale, natürlichsprachliche Antwort generiert.
```

### Cross-DF-Coupling & Lazy-Import-Stubs

Um die strikte Isolierung der Dark-Factories während lokaler Entwicklungszyklen aufrechtzuerhalten, wird das Cross-DF-Coupling (die Abhängigkeit zu W36 und W37) über **Lazy-Import-Stubs** gelöst. 

Das bedeutet, dass die Extension nicht hart an Module wie `df-pms-mews-adapter` gebunden ist. Erst zur Laufzeit (innerhalb des `handle_function_call` Routers) wird versucht, die Adapter-Klassen zu importieren. Schlägt dieser Import fehl (da die entsprechende Factory im aktuellen Workspace nicht gebaut ist), greift die Extension automatisch auf interne Mocks zurück, sofern die Sandbox dies erlaubt.

## 4. Sandbox-Modus und Umgebungssteuerung

Sicherheit und Determinismus sind in der automatisierten Ausführung oberstes Gebot. Die Extension verfügt über zwei strikt getrennte Betriebsmodi, die über Umgebungsvariablen gesteuert werden.

### Sandbox-Default (Mock-Modus)
Ist die Variable `DF_HEYLOU_MISTRAL_EXT_ENABLED=false` gesetzt (oder fehlt sie komplett), läuft die Extension im sicheren Sandbox-Modus.
- Das Mistral-Modell erhält ausschließlich synthetische und deterministische Antworten aus lokalen JSON-Mocks.
- Der Aufruf an externe PMS-Systeme (W36) oder reale OTAs (W37) wird vollständig unterbunden.
- Dies ist der Standard-Modus für CI/CD-Pipelines und lokale Unit-Tests.

### Produktions-Modus (Real-Mode)
Um echte API-Aufrufe an die angeschlossenen Backends auszuführen, müssen folgende Voraussetzungen zwingend erfüllt sein:
1. `DF_HEYLOU_MISTRAL_EXT_ENABLED=true`
2. Das Vorhandensein eines gültigen `PHRONESIS_TICKET`s.
3. Ein valider `MISTRAL_API_KEY`.

Fehlt eine dieser Komponenten, verweigert die Extension den Start und terminiert mit einem Fatal Error (Fail-Safe-Mechanismus).

## 5. Sicherheitsrichtlinien: K11-K16 & LC1-LC5

Die Architektur der Mistral-Extension implementiert die strengen Sicherheits- und Audit-Richtlinien der Dark-Factories.

### K13: Pre-Action-Verification
Kein Function Call (insbesondere nicht `book_direct`) darf ausgeführt werden, ohne dass eine vorherige Autorisierung stattgefunden hat. Die Methode `auth_handler.verify_phronesis_ticket()` wird synchron vor jedem Routing-Schritt aufgerufen. Ist das Ticket abgelaufen, manipuliert oder nicht vorhanden, wird der Request mit einem `403 Forbidden` Exception-State abgebrochen und der Vorfall geloggt.

### K16: mkdir-Mutex
In den Initialisierungsskripten (`scripts/run-*.sh`) wird das K16-Pattern angewendet. Durch die Verwendung von atomaren Verzeichnis-Erstellungs-Befehlen (`mkdir`) als Lock-Mechanismus (Mutex) wird garantiert, dass die Extension nicht in Race-Conditions gerät, falls das System versucht, mehrere Instanzen des Routers zeitgleich hochzufahren.

### AuditLogger (HMAC-SHA256 JSONL)
Jede ausgeführte Funktion, ihre Parameter und das daraus resultierende Backend-Resultat werden in einem manipulationssicheren Audit-Log erfasst.
- Das Format der Logs ist `JSONL` (JSON-Lines), optimiert für nachgelagerte Ingestion durch Big-Data-Pipelines.
- Jeder Log-Eintrag wird kryptografisch via HMAC-SHA256 signiert. Dies stellt sicher, dass nachträgliche Änderungen am Log (z.B. durch kompromittierte Container) sofort detektiert werden.

## 6. Deployment: LaunchAgent & Test-Suite

Die Extension ist als persistenter Background-Service für macOS-basierte Host-Infrastrukturen (bzw. entsprechende Unix-Derivate im CI-Kontext) konzipiert.

### LaunchAgent Plist Configuration

Das Scheduling und das automatische Neustarten des Services übernimmt der macOS `launchd` Daemon.

- **Plist-Datei:** `scripts/com.kemmer.df-heylou-mistral-extension.plist`
- **Working Directory:** `/Users/make/Projects/dark-factories/df-heylou-mistral-extension`
- **RunAtLoad:** `true` (Startet sofort, wenn das System hochfährt oder der Agent geladen wird).
- **StartInterval:** `7200` Sekunden (2 Stunden). Der Prozess re-evaluiert alle 2 Stunden seinen State, holt neue Phronesis-Tickets und aktualisiert bei Bedarf die Mistral-API-Session.

### Quality Assurance & Testing

Die Verifikation der Extension erfolgt über `pytest`. Die Tests decken sowohl den Sandbox-Fallback ab als auch die korrekte Ablehnung von manipulierten Phronesis-Tickets.

```bash
# Ausführen der kompletten Test-Suite mit Verbose-Output
pytest tests/ -v
```

Die Test-Suite beinhaltet Mock-Objekte für die Mistral API, sodass keine echten (kostenpflichtigen) Tokens während des CI-Durchlaufs verbraucht werden.
